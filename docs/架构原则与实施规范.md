# FUXA 定制化架构原则与实施规范

> **版本**: v2.0 | **日期**: 2026-05-13 | **状态**: 已批准 |
> **基于**: 科控物联最佳实践 + 方案A实施经验总结

## 一、核心原则

### 1.1 总则

> **"能通过配置实现就不用改代码，必须改代码就要有完整记录"**

### 1.2 修改优先级矩阵

| 优先级 | 实施方式 | 适用场景 | 升级风险 | 审批要求 |
|--------|---------|---------|---------|---------|
| **P0** | 数据库配置 (`_appdata/project.fuxap.db`) | Header配置、视图属性、标签绑定 | ✅ 无风险 | 无需审批 |
| **P1** | FUXA原生API (`layout.customStyles`等) | 自定义CSS、主题样式 | ✅ 无风险 | 无需审批 |
| **P2** | 资源/配置文件修改 | Logo替换、地图源、依赖包 | ⚠️ 低风险 | 记录即可 |
| **P3** | 组件样式/业务逻辑修改 | 深度UI定制、功能增强 | ⚠️ 中风险 | 文档+测试 |
| **P4** | 核心框架代码修改 | 数据库结构、通信协议 | ❌ 高风险 | **禁止** |

## 二、各类修改详解

### 2.1 P0: 数据库配置（推荐 ✅）

**实施方式**: 通过脚本修改 `_appdata/project.fuxap.db`

**适用场景**:
- ✅ Header导航栏配置（参数显示、报警按钮等）
- ✅ 视图页面属性（背景色、尺寸等）
- ✅ 标签/变量绑定关系
- ✅ 导航菜单配置
- ✅ 报警规则和通知设置

**优势**:
- 完全不涉及源代码
- 可安全升级FUXA版本
- 配置可通过脚本自动化
- 易于版本管理和回滚

**示例脚本**:
```javascript
// server/configure-header.js
const sqlite3 = require('sqlite3').verbose();
const db = new sqlite3.Database('_appdata/project.fuxap.db');

db.get("SELECT value FROM general", (err, row) => {
    const general = JSON.parse(row.value);
    
    // 修改Header配置
    general.header.bkcolor = '#1a1a2e';
    general.header.items = [...];
    
    // 保存到数据库
    db.run("UPDATE general SET value = ?", [JSON.stringify(general)]);
});
```

### 2.2 P1: FUXA原生API使用（推荐 ✅）

**实施方式**: 使用FUXA提供的扩展点

#### 2.2.1 customStyles - 自定义CSS注入

**位置**: `general.layout.customStyles`

**功能**: 向FUXA应用注入全局CSS样式

**适用场景**:
- ✅ 主题色彩定制
- ✅ 字体排版优化
- ✅ 交互动画效果
- ✅ 响应式布局调整

**示例**:
```css
/* 通过 layout.customStyles 注入 */
.header {
    background-color: #1a1a2e !important;
    height: 48px !important;
}

.header .header-items-button button {
    font-size: 16px !important;
    font-weight: 700 !important;
}
```

**注入方法**:
参见 `server/inject-custom-css.js`

#### 2.2.2 其他原生API

| API字段 | 位置 | 用途 |
|---------|------|------|
| `layout.theme` | general.layout | 主题切换（dark/default） |
| `navigation.items` | general.layout.navigation | 导航菜单项 |
| `header.items` | general.header | Header项目数组 |
| `views[].profile` | views表 | 视图尺寸和背景 |

### 2.3 P2: 资源/配置文件修改（允许 ⚠️）

**定义**: 替换资源文件或修改配置参数，不改变代码逻辑

**适用场景**:
- ✅ 品牌标识替换（Logo、图标、Favicon）
- ✅ 地图服务源更换
- ✅ 第三方插件依赖添加
- ✅ 默认参数调整

**必须包含的记录**:

#### 2.3.1 修改登记表

每个P2修改必须在 [定制化修改清单.md](./定制化修改清单.md) 中登记：

```markdown
### 修改 #001: 地图源更换

- **文件**: `client/src/app/maps/maps-view/maps-view.component.ts`
- **修改类型**: P2 - 配置参数
- **修改内容**:
  ```typescript
  // 替换前
  url: 'https://{s}.tile.openstreetmap.org'
  
  // 替换后
  url: 'https://tile-c.openstreetmap.fr/hot'
  ```
- **原因**: 提升国内访问速度
- **影响范围**: 仅地图显示功能
- **升级兼容性**: ✅ 可安全升级（仅URL变更）
- **回滚方案**: 还原原始URL
- **测试验证**: ✅ 已测试地图正常加载
- **修改日期**: 2026-04-15
- **修改人**: 开发团队
```

### 2.4 P3: 组件样式/逻辑修改（谨慎 ⚠️）

**定义**: 修改FUXA组件的样式文件或业务逻辑代码

**适用场景** (仅在P0/P1无法实现时):
- ⚠️ customStyles无法满足的深度样式定制
- ⚠️ 需要修改组件交互逻辑的功能增强
- ⚠️ 集成第三方监控系统（如Stardust APM)

**严格要求**:

#### 2.4.1 必须提供的文档

1. **技术设计文档**
   - 修改原因和目标
   - 技术方案对比（为什么不能用P0/P1/P2）
   - 详细实现方案

2. **修改影响分析**
   - 影响的模块列表
   - 对升级的影响评估
   - 回滚策略

3. **测试报告**
   - 单元测试结果
   - 集成测试结果
   - 性能测试数据

4. **维护指南**
   - 升级时的合并策略
   - 冲突解决预案

#### 2.4.2 示例：Stardust APM集成（科控物联案例）

**文件**: `server/main.js`, `server/runtime/stardust.js`

**文档**: [科控物联优化.MD 第七章](../科控物联优化.MD#七-stardust-apm-集成)

**合规性检查**:
- ✅ 有明确的使用说明
- ✅ 有功能特性列表
- ✅ 有配置参数说明
- ✅ 可通过配置禁用（不影响核心功能）

### 2.5 P4: 核心框架代码修改（禁止 ❌）

**定义**: 修改FUXA的核心框架代码

**禁止事项**:
- ❌ 修改数据库表结构
- ❌ 修改通信协议实现
- ❌ 修改标签系统核心逻辑
- ❌ 修改SVG渲染引擎
- ❌ 修改权限认证机制

**原因**:
- 极高的升级冲突风险
- 可能引入难以排查的bug
- 违反软件架构分层原则

**替代方案**:
- 使用P0-P3的方式实现需求
- 向FUXA官方提交Feature Request
- 开发独立的插件/扩展

## 四、工作流程

### 4.1 新功能实施决策树

```
开始实施新功能
    ↓
能否通过数据库配置(P0)实现？
    ├── 是 → 使用P0方式 ✅
    └── 否 ↓
        
能否使用FUXA原生API(P1)实现？
    ├── 是 → 使用P1方式 ✅
    └── 否 ↓
        
是否仅为资源/配置文件修改(P2)？
    ├── 是 → 使用P2方式 + 记录到修改清单 ⚠️
    └── 否 ↓
        
是否绝对必要且无替代方案？
    ├── 否 → 重新评估需求或提交官方FR ❌
    └── 是 ↓
        
使用P3方式 + 完整文档 + 测试 + 审批 ⚠️⚠️
```

### 4.2 修改申请流程（P2/P3级别）

```
1. 提交修改申请
   ├─ 说明修改内容和原因
   ├─ 提供技术方案
   └─ 评估影响范围
   
2. 审批
   ├─ P2: 自动审批（仅需记录）
   └─ P3: 需要技术负责人审批
   
3. 实施
   ├─ 按照规范进行修改
   ├─ 编写必要文档
   └─ 执行测试
   
4. 登记
   ├─ 更新[定制化修改清单.md]
   ├─ 更新相关技术文档
   └─ 通知团队成员
```

## 六、升级策略

### 6.1 FUXA版本升级流程

```
1. 升级前准备
   ├─ 备份数据库 (_appdata/project.fuxap.db)
   ├─ 备份自定义配置脚本
   ├─ 阅读[FUXA-升级指南.md]
   └─ 检查当前P2/P3修改清单

2. 执行升级
   ├─ 拉取最新FUXA代码
   ├─ 解决合并冲突（如有）
   └─ 重新构建

3. 升级后验证
   ├─ 测试所有P0/P1配置功能
   ├─ 验证P2修改是否仍生效
   ├─ 检查P3修改是否需要适配
   └─ 全面回归测试

4. 问题处理
   ├─ 如有冲突，参照修改清单逐个修复
   ├─ 更新修改清单（标记已适配）
   └─ 记录遇到的问题和解决方案
```

### 6.2 各级别的升级风险

| 级别 | 升级风险 | 处理策略 |
|------|---------|---------|
| P0 | ✅ 无风险 | 直接使用，无需处理 |
| P1 | ✅ 无风险 | 重新运行注入脚本即可 |
| P2 | ⚠️ 低风险 | 检查文件是否被覆盖，按清单重新应用 |
| P3 | ⚠️ 中风险 | 详细对比代码差异，可能需要适配新API |
| P4 | ❌ 禁止 | 不应存在此类修改 |

## 七、最佳实践

### 7.1 推荐做法

1. **优先使用配置**
   - 90%的需求应通过P0/P1实现
   - 保持源代码的纯净性

2. **脚本化管理**
   - 所有P0/P1操作都写成可重复执行的脚本
   - 纳入版本控制系统

3. **完整记录**
   - 每个P2/P3修改都有据可查
   - 包含足够的信息供他人理解和维护

4. **定期审查**
   - 每季度审查一次修改清单
   - 评估是否有P3可以降级为P2或P1
   - 清理不再需要的修改

5. **测试先行**
   - P3修改必须有自动化测试
   - 回归测试覆盖所有修改点

### 7.2 反面教材（避免）

1. ❌ "快速修复"直接改源码而不记录
2. ❌ 复制整个文件而非最小化修改
3. ❌ 修改后不测试就部署
4. ❌ 升级时不检查兼容性
5. ❌ 多人同时修改同一文件无协调
