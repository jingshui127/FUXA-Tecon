# 科控物联定制优化清单

> 当前维护基线：FUXA PRO `1.3.4-PRO`
>
> 本文档用于查看科控物联定制功能、已完成优化、持续维护事项和后续待规划内容。命令、路径和版本仅以当前项目实际规范为准；历史版本方案不作为当前操作依据。

## 一、当前基线

| 项目 | 当前约定 |
|---|---|
| 定制版本 | `1.3.4-PRO` |
| 正式产物 | `artifacts\\fuxa-pro-headless.exe` |
| 打包目标 | Node.js 18，`node18-win-x64` |
| 默认端口 | `1881` |
| 运行数据 | `<EXE目录>\\data\\` |

## 二、已完成并纳入当前版本

### 1. 品牌与定制化

- [x] 启动信息使用科控物联技术支持信息。
- [x] 支持通过 EXE 同级 `customization\\` 目录覆盖品牌配置。
- [x] 支持外部 `config.json`、`logo.svg` 和 `favicon.ico`，不修改 EXE 内置文件即可更换品牌资源。
- [x] 未配置外部品牌文件时，继续使用内置默认配置。

### 2. 通讯协议与插件

当前支持或维护的通讯插件：

| 协议/功能 | 依赖 | 当前状态 |
|---|---|---|
| Modbus TCP/RTU | `modbus-serial` | 已接入，按网页插件方式维护 |
| S7-1200/1500 | `node-snap7` | 已接入，Node.js 18 原生模块 |
| OPC UA | `node-opcua` | 已接入，按网页插件方式维护 |
| BACnet | `node-bacnet` | 已接入，按网页插件方式维护 |
| ADS/Beckhoff | `ads-client` | 已接入，按网页插件方式维护 |
| ODBC | `odbc@2.4.9` | 作为原生插件预置并验证 |
| 图表渲染 | `chartjs-node-canvas@3.2.0`、`canvas@2.11.2` | 作为原生插件预置并验证 |

维护要求：

- [x] 通讯插件优先从 FUXA 网页插件管理页面安装。
- [x] 迁移时复制 EXE 和完整 `data\\` 目录，保留插件、项目和配置。
- [x] 原生插件必须在 Node.js 18 / Windows x64 环境实际加载验证。
- [x] 图表插件必须完成实际图表渲染，不能只检查 npm 安装成功。
- [ ] 后续新增原生通讯插件时，补充目标 ABI、DLL 和实际连接验证记录。

### 3. S7 稳定性

- [x] 断开连接时避免调用可能触发 native 冲突的底层 `Disconnect()`。
- [x] 连续异常或 overload 后清理旧客户端并强制全新重连。
- [x] 读取变量、读取 DB 和获取错误信息前增加客户端状态保护。
- [x] 进程退出时清理 S7 客户端引用，降低 native 清理冲突。

后续维护重点：

- [ ] 使用真实 S7-1200/1500 设备进行长时间读写、断线、重连和进程退出测试。
- [ ] 记录不同 PLC 固件、连接数量和轮询周期下的稳定性结果。

### 4. 项目保存与运行稳定性

- [x] 仅修改视图时跳过不必要的设备服务重启。
- [x] 保存项目时先响应客户端，再异步处理必要的服务重启。
- [x] 设备启动循环增加单设备异常保护，避免一个设备影响其他设备。
- [x] Headless 模式将可写运行数据放在 EXE 同级 `data\\`，避免写入 pkg 快照目录。
- [x] 文件上传目录使用可写数据目录，避免 pkg 环境下创建目录失败。
- [x] SIGINT 退出流程等待 FUXA 清理逻辑完成后再退出。

后续维护重点：

- [ ] 验证大型项目保存、仅改视图保存、设备配置变更保存三种场景。
- [ ] 验证上传/下载、自定义组件和业务资源在 EXE 环境下的完整读写流程。

### 5. Node-RED 集成

- [x] 管理编辑器固定使用 `/flows`。
- [x] 保留 `/nodered` 作为兼容入口。
- [x] Dashboard 和 HTTP 节点固定使用 `/dashboard`。
- [x] Node-RED 流程保存到 EXE 同级数据目录。
- [x] 修复 pkg 环境中内部模块路径解析问题。
- [x] 修复 Node-RED registry 的 pkg 元数据读取。
- [x] 处理 Node-RED 4.1.10 对 `got` 的动态加载问题。
- [x] 保留 `nodeRedAuthMode` 配置，默认使用安全模式。

发布前检查：

- [ ] 启动日志包含 `[Node-RED] Started at /flows (dashboard: /dashboard)`。
- [ ] `/`、`/flows`、`/nodered` 和 `/dashboard` 均完成健康检查。
- [ ] 启动日志不包含 `Cannot find package 'got'`。
- [ ] 确认流程、日志和业务数据没有写入 `C:\snapshot\\...`。

### 6. 字体、报表和遥测

- [x] 修复字体处理中的编码问题，避免非 ASCII 字符显示异常。
- [x] 对 fontkit 使用懒加载，降低 pkg 启动阶段加载失败风险。
- [x] 已关闭 Stardust APM 遥测，避免无关网络请求和错误日志影响运行判断。
- [ ] 后续升级 fontkit、pdfmake 或 Node.js 时，重新验证中文字体、PDF 和报表渲染。

## 三、当前构建与发布维护项

- [x] 构建前同步服务端源码、前端编译产物和 Headless 入口。
- [x] 使用 `npm ci --omit=dev --no-audit --no-fund` 安装 Headless 依赖。
- [x] 执行 Node-RED patch，并验证 `[patch-nodered] verification passed`。
- [x] 使用 Node.js 18、`node18-win-x64` 和 `compression: "None"` 执行 pkg。
- [x] 只有日志出现 `[BUILD] SUCCESS` 才认定正式 EXE 构建成功。
- [x] 重新打包只覆盖正式 EXE，不删除或清空已有 `data\\`。
- [x] 禁止多个 npm、pkg 或完整构建任务同时操作 `fuxa-headless\\node_modules`。
- [x] 禁止将 `artifacts\\`、运行时 `data\\`、临时日志或异常嵌套目录作为提交内容。
- [ ] 恢复或确认 GitHub Actions 账户 billing，使自动构建可以稳定执行。
- [ ] 评估并处理 pkg 的 `Failed to make bytecode` 警告；在确认不影响运行前，不将其当作构建失败。

## 五、明确不再作为当前方案的内容

以下内容属于历史方案，不应直接照搬：

- 旧版本 `1.3.1` 的绝对路径和部署目录。
- 直接修改已编译 JS 文件作为日常地图或品牌维护方式。
- 在 `server` 目录中手工重复安装网页通讯插件作为默认流程。
- 旧版 `FuxaPro-Single.exe` 等非当前正式产物名称。
- 将 `/nodered` 当作当前主要管理入口。
- 将运行时 `data\\`、`artifacts\\` 或临时构建目录纳入源码提交。
- 仅执行 `npm ci` 或仅复制文件后就认定 EXE 已完成构建。
